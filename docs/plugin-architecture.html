Architecture note

The Context Layer

How to structure shared AI tooling so a delivery org stops re-deriving what it already knows — and what that actually costs.

Anna Knoll · August 2026

01 / Problem

The expensive knowledge is the unwritten kind

An AI assistant starts every session with amnesia. That is a manageable problem when the missing knowledge is public — it can look things up. It is an expensive problem when the missing knowledge is organizational: how this customer names things, which sandbox is safe to point at, who approves a deployment, what was promised in the demo, why the obvious approach was abandoned last quarter.

Without that, the assistant produces work that is locally plausible and organizationally wrong. That is worse than no help, because now a senior person has to review it.

The same gap is what makes the pre-sales-to-delivery handoff expensive. One team scopes and demos a solution; another inherits a customer with expectations, a half-documented org, and a chat thread where the real constraints were discussed. Context is lost exactly where it costs the most.

02 / Primitives

Four answers, sorted by when they load

Every piece of a context layer is one of four things. The useful way to tell them apart is not what they contain — it is when they enter the model's working memory, because that is what you pay for.

PrimitiveAnswersLoadsCost
Rules"Always work this way here"On demand, by pointerOnly when read
Skills"When doing this, here are the steps"On demand, by name or matchOnly when invoked
Agents"Send a specialist with its own context"When delegated toIts own window, not yours
Hooks"Never let this happen"Automatically, on an eventNear zero — it is a script
Scripts"Don't ask a model to do this at all"Called by the aboveZero tokens

The last row is the highest-leverage idea and the easiest to skip. Any time a prompt says "carefully check each of the following two hundred things," that is a script nobody has written yet. Let deterministic code do the scanning and reserve the model for the judgment the code cannot express.

The design rule

A hook is the only layer that cannot be talked out of it. Rules and skills are prose, and a model can drift from prose. When something must be guaranteed rather than usually observed, it has to be a script bound to an event.

03 / Mechanism

Pointers, not content

The naive implementation loads every rule into every session. It works, and it quietly taxes every conversation — including the ones that never touch the rules it loaded.

The better shape: a session-start hook resolves where it is, then injects a short index — what this project is, and the paths to the rules that apply, each with a one-line "read this when." The model pulls the two it needs and ignores the rest.

Which rules make the index is itself two decisions, and both are needed. By archetype: the engagement declares its type, and each rule declares which types it serves. By detection: the hook looks at what is actually in the working tree, because the declared type is always a little wrong — a service with no front end still turns out to ship a handful of templates, and the interface bar applies to those whether or not anyone updated the manifest.

Each rule declares its own applicability, so adding one requires no change to the hook. And the index records why each rule was selected, which turns a wrong selection into something you can see instead of something you have to reverse-engineer.

04 / Structure

Two layers, and neither works alone

This is the load-bearing architectural decision, and it is the one most implementations get wrong by collapsing it into a single layer.

Shared tooling holds two kinds of content with different lifetimes. Standards are identical across every engagement and change slowly: platform non-negotiables, review expectations, deployment discipline, the procedures a firm has agreed on. Engagement context is different for every customer and changes weekly: their org shape, their naming conventions, their change-control process, what has already been decided and what is still open.

Put standards in each engagement and you get N copies drifting apart. Put engagement context at the shared layer and every customer inherits every other customer's specifics, which is both useless and a disclosure problem.

05 / Payoff

The handoff becomes a file

Everything above is plumbing for one outcome. When a session produces something that matters — a scope, a set of constraints, a decision and its reasoning, a list of what is still unresolved — it writes it to disk in the engagement layer rather than leaving it in a chat transcript.

Two things follow. Human context stays readable, because nobody scrolls past a four-hundred-line generated spec to find the one question they were asked. And the work becomes durable: a document can be diffed, reviewed, and handed to the next person or the next session as a real artifact.

06 / Mapping

What each layer holds in a platform engagement

Nothing above is specific to a vendor. Mapped onto a Salesforce delivery context, the pieces land like this.

PieceIn an engagement
Engagement charterPer customer: org shape, licensed clouds, integration surface, sandbox strategy, who decides what
ArchetypesEngagement types that pre-load different content — a Service Cloud migration, a Data Cloud activation, an Agentforce pilot each carry different rules and checklists
Shared rulesPlatform non-negotiables: governor limits, no hardcoded IDs, metadata deployment discipline, security review expectations
Local rulesThe customer's own conventions: naming standards, change-control process, release calendar
GatesNever deploy to production without a validation-only run. Flag a hardcoded org ID. Block a change touching a managed package.
ScriptsDeterministic CLI and Metadata API work: org diffs, permission-set audits, test-coverage checks
ArtifactsThe scope, constraints, decisions and open questions the next session inherits

The gates are the row that changes behavior. Everything else is advice a busy person can skip.

07 / Limits

Where this breaks

Four objections that a room with real delivery experience will raise, and the honest answers.

Two different things are called "agents"

Customer-facing agents run in the customer's org and are the product being sold. The agents in this pattern are developer-side — they help the engineer build. Conflating them gets the whole idea dismissed by anyone technical. The defensible claim is narrower and stronger: better internal build context produces better customer-facing deployments, faster.

Platform metadata is not a filesystem

Much of what makes this work assumes source control: hooks on git operations, scripts diffing files, branch discipline. Source-tracked development gives you an approximation, but a declarative change made in a sandbox by a customer admin is invisible to all of it. Any version of this pitch that assumes clean source control gets punctured by the first person who has actually run a pilot.

Customer environments carry compliance constraints

Which model, hosted where, seeing whose data, retained how long, under whose agreement. A pattern that is fine on a laptop needs a different answer before it touches a regulated customer's org. Have that answer, or scope it out of v1 explicitly.

The adoption curve is the real risk

A mature context layer is years of accumulated friction written down. A firm cannot buy that; it has to accumulate it. What is available on day one is the structure plus a seeded set of platform rules, and the honest framing that it compounds. Overpromising immediate value is how these initiatives die in month three.

08 / Sequence

What to build first

The most common failure is starting with the org chart of a larger operation — a full agent mesh, an installer, a dozen archetypes — before any of it is earned. The order that works runs the other way.

  • Write the charter and three or four platform rules. Prose, in files. That is most of the value.
  • Add one gate that blocks something genuinely dangerous, once prose has visibly failed to prevent it.
  • Add a script the first time you catch yourself asking a model to check fifty things.
  • Add a procedure the second time you explain the same process to someone.
  • Add specialist agents only when a task reliably exhausts the context window.

Each step should be traceable to a specific thing that went wrong twice. A layer added before its second occurrence is a layer nobody uses, and it makes the ones that matter harder to find.

A credible pilot

One archetype, one gate, one artifact. Pick a narrow engagement type, write the charter and a few rules, add a gate that blocks something real, run a build task, then hand the artifact to a second session that has never seen the first. The second session picking up cleanly is the demonstration, and it fits in ten minutes.
