The Context Layer

How to structure shared AI tooling so a delivery org stops re-deriving what it already knows — and what that actually costs.

Anna Knoll · August 2026

01 / Problem

Where the time actually goes

Build and validate take what they take. What collapses is the re-derivation at the front and the loss at the back.

Detail

An AI assistant starts every session with amnesia. That is manageable when the missing knowledge is public — it can look things up. It is expensive when the missing knowledge is organizational: how this customer names things, which sandbox is safe to point at, who approves a deployment, what was promised in the demo, why the obvious approach was abandoned last quarter.

Without it, the assistant produces work that is locally plausible and organizationally wrong. That is worse than no help, because now a senior person has to review it.

The same gap is what makes the pre-sales-to-delivery handoff expensive. One team scopes and demos a solution; another inherits a customer with expectations, a half-documented org, and a chat thread where the real constraints were discussed. Context is lost exactly where it costs the most.

02 / Primitives

Five answers, sorted by when they load

The useful way to tell them apart is not what they contain. It is when they enter working memory, because that is what you pay for.

PrimitiveAnswersLoadsCost
Rules"Always work this way here"On demand, by pointerOnly when read
Skills"When doing this, here are the steps"On demand, by name or matchOnly when invoked
Agents"Send a specialist with its own context"When delegated toIts own window, not yours
Hooks"Never let this happen"Automatically, on an eventNear zero — it is a script
Scripts"Don't ask a model to do this at all"Called by the aboveZero tokens
Detail

The last row is the highest-leverage idea and the easiest to skip. Any time a prompt says "carefully check each of the following two hundred things," that is a script nobody has written yet. Let deterministic code do the scanning and reserve the model for the judgment the code cannot express.

A hook is the only layer that cannot be talked out of it. Rules and skills are prose, and a model can drift from prose. When something must be guaranteed rather than usually observed, it has to be a script bound to an event.

03 / Mechanism

Pointers, not content

Naming a rule costs a line. Loading it costs its full length in every session, forever.

Detail

The naive implementation loads every rule into every session. It works, and it quietly taxes every conversation — including the ones that never touch the rules it loaded.

The better shape: a session-start hook resolves where it is, then injects a short index — what this engagement is, and the paths to the rules that apply, each with a one-line "read this when." The model pulls the two it needs and ignores the rest.

Which rules make the index is itself two decisions. By archetype: the engagement declares its type, and each rule declares which types it serves. By detection: the hook looks at what is actually in the working tree, because the declared type is always a little wrong — a service with no front end still turns out to ship a handful of templates, and the interface bar applies to those whether or not anyone updated the manifest.

Each rule declares its own applicability, so adding one requires no change to the hook.

04 / Structure

Two layers, and neither works alone

Collapse them into one and you are choosing between stale standards and leaked customer specifics.

Detail

This is the load-bearing architectural decision, and the one most implementations get wrong by collapsing it into a single layer.

Shared tooling holds two kinds of content with different lifetimes. Standards are identical across every engagement and change slowly: platform non-negotiables, review expectations, deployment discipline, the procedures a firm has agreed on. Engagement context is different for every customer and changes weekly: their org shape, their naming conventions, their change-control process, what has been decided and what is still open.

Put standards in each engagement and you get N copies drifting apart. Put engagement context at the shared layer and every customer inherits every other customer's specifics — which is a disclosure problem, not just an architecture problem.

05 / Payoff

The handoff becomes a file

A second session that never saw the first picks up cleanly. That is the whole thesis.

Detail

When a session produces something that matters — a scope, a set of constraints, a decision and its reasoning, a list of what is still unresolved — it writes it to disk in the engagement layer rather than leaving it in a chat transcript.

Two things follow. Human context stays readable, because nobody scrolls past a four-hundred-line generated spec to find the one question they were asked. And the work becomes durable: a document can be diffed, reviewed, and handed to the next person or the next session as a real artifact.

What each piece is, in a platform engagement

07 / Limits

Where this breaks

Four objections a room with real delivery experience will raise, and the honest answers.

Two different things are called "agents"

Customer-facing agents run in the customer's org and are the product being sold. The agents in this pattern are developer-side — they help the engineer build. Conflating them gets the whole idea dismissed by anyone technical.

The defensible claim is narrower and stronger: better internal build context produces better customer-facing deployments, faster.

Platform metadata is not a filesystem

Much of this assumes source control: hooks on git operations, scripts diffing files, branch discipline. A declarative change made in a sandbox by a customer admin is invisible to all of it, and production orgs have no source tracking to fall back on.

The gap is measurable, though. A script can diff deployed metadata against the repository and report only its verdict — a dozen lines, not a dump of XML. That is the deterministic-first pattern applied exactly where it pays.

Where it runs is the design decision. Not at session start: without source tracking that check is a full retrieve, which is tens of seconds to minutes, and a hook that stalls every session gets disabled within a week. It belongs on the deploy command, where blocking for thirty seconds is obviously worth it — or on a schedule that writes a drift report the session merely reads, reporting both the drift and the age of the report.

What it still cannot see: profiles and permission sets retrieve only partially, so their diffs are unreliable; flow versions and active states are awkward; and data is not metadata at all, so a picklist value changed under a running agent is invisible to the entire approach. Drift detection narrows the gap. It does not close it, and it never tells you why something changed.

Customer environments carry compliance constraints

Which model, hosted where, seeing whose data, retained how long, under whose agreement. A pattern that is fine on a laptop needs a different answer before it touches a regulated customer's org.

Have that answer, or scope it out of v1 explicitly. Discovering it in month two is worse than declining it in week one.

The adoption curve is the real risk

A mature context layer is years of accumulated friction written down. A firm cannot buy that; it has to accumulate it.

What is available on day one is the structure plus a seeded set of platform rules, and the honest framing that it compounds. Overpromising immediate value is how these initiatives die in month three.

08 / Sequence

What to build first

Each layer should trace to a specific thing that went wrong twice.

  1. Write the charter and three or four platform rules. Prose, in files. That is most of the value.
  2. Add one gate that blocks something genuinely dangerous, once prose has visibly failed to prevent it.
  3. Add a script the first time you catch yourself asking a model to check fifty things.
  4. Add a procedure the second time you explain the same process to someone.
  5. Add specialist agents only when a task reliably exhausts the context window.
Detail

The most common failure is starting with the org chart of a larger operation — a full agent mesh, an installer, a dozen archetypes — before any of it is earned. A layer added before its second occurrence is a layer nobody uses, and it makes the ones that matter harder to find.

A credible pilot: one archetype, one gate, one artifact. Pick a narrow engagement type, write the charter and a few rules, add a gate that blocks something real, run a build task, then hand the artifact to a second session that has never seen the first. The second session picking up cleanly is the demonstration, and it fits in ten minutes.
